# Railway Deployment — Thrive Causemetics Launch Intelligence Hub

## Service

- **Repo:** this repository (deploy branch: `main`)
- **Build:** Dockerfile (`railway.json` pins builder + healthcheck)
- **Start command:** `node server.js` — binds `0.0.0.0:$PORT` (Railway injects `PORT`)
- **Healthcheck:** `GET /api/health` → `{ ok, dataCutoff, generatedAt, launches }`
  (fails if the committed `data.js` snapshot is unreadable)

## How data stays fresh

The container is a static file server — **no database, no Snowflake
credentials, no runtime secrets**. Data lives in `data.js`, regenerated by
GitHub Actions (`.github/workflows/refresh-data.yml`) daily at 6:05am
America/Los_Angeles — pinned to LA time year-round via one cron entry per DST
offset — from Snowflake DAASITY_DB and committed to `main`. Each data commit
triggers a Railway redeploy, so the live site is always ≤1 day fresh with
zero container-side configuration.

### Why a second service triggers the refresh

GitHub's `schedule` trigger queues under load. Measured over two weeks, every
scheduled run of this workflow started **86–163 minutes after its slot**, so
the nominally-6am data was landing 7:30–8:45am PT — anyone opening the
dashboard at 7am saw the previous day's cutoff. Every `workflow_dispatch` run
started with **zero delay**.

So the schedule of record is a Railway **cron service**
(`trigger-refresh.js`) that dispatches the workflow at 6:00am LA. The
workflow's own cron stays as a safety net; a second run the same day
regenerates identical data, `git diff --quiet` sees no change, and nothing is
committed.

Read `meta.generatedAt` / `meta.dataCutoff` (also on `/api/health`) rather
than assuming a run happened — that is the only reliable freshness signal.

Snowflake credentials live only in **GitHub repository secrets**
(`SNOWFLAKE_*` — see `.env.example`), never in Railway Variables. The trigger
service holds only `REFRESH_DISPATCH_TOKEN`, which can dispatch workflows and
nothing else.

## Routes

| Route | Purpose |
|---|---|
| `/` | Launch Intelligence Hub (launch cards) |
| `/launch.html?id=<launch-id>` | Per-launch dashboard |
| `/api/health` | Healthcheck with data-freshness metadata |

Pipeline internals (`scripts/`, `config/`, `.github/`) are excluded from the
image and blocked by the server's allowlist.

## Human-gated Railway steps (do these in the Railway UI)

1. Create the Railway service from this GitHub repo (New Project → Deploy
   from GitHub repo), deploy branch `main`.
2. No variables are required — `PORT` is injected automatically.
3. Optional: attach the service to the internal portal's private network so
   the `thrive-knowledge-app` proxy can rewrite `/launch-dashboards/*` to it
   (same pattern as glowing-launch-pad, port 8080).

### Refresh trigger cron service

A second Railway service, from this same repo, keeps the daily refresh on
time. It runs for a few seconds and exits — it serves no traffic.

1. Create a fine-grained GitHub PAT at
   https://github.com/settings/personal-access-tokens/new
   - Repository access: **only** `thrivecausemetics/Launch-Dashboard`
   - Permissions: **Actions → Read and write** (nothing else — this token must
     not be able to read Snowflake secrets or push code)
   - Set an expiry and a calendar reminder to rotate it; a silently expired
     token means the trigger stops and only the late GitHub cron remains.
2. New service in the same project → Deploy from this GitHub repo, branch
   `main`. Name it `launch-dashboard-refresh-trigger`.
3. Settings → **Start Command**: `node trigger-refresh.js`
4. Settings → **Cron Schedule**: `0 13,14 * * *`
   Railway cron is UTC and DST-unaware, so both hours fire; the script
   dispatches only when it is 6am in Los Angeles, which holds 6:00am LA
   year-round. (Unlike the GitHub workflow, a wall-clock check is correct
   here — this scheduler is punctual.)
5. Settings → disable the healthcheck. A cron service that exits is not a
   web server and will otherwise be marked unhealthy.
6. Variables → `REFRESH_DISPATCH_TOKEN` = the PAT from step 1.

Verify with **Deploy** (a manual run): outside the 6am LA hour it should log
`out-of-season cron entry, nothing to dispatch` and exit 0. To test the
dispatch path itself, run the workflow once from the GitHub Actions UI.

## Slack alerts (human-gated setup)

The daily refresh can post the top launch alerts to Slack. It stays silent
until `SLACK_WEBHOOK_URL` exists, so nothing breaks before this is done.

**Creating the app (needs someone who can install Slack apps):**

1. Create the destination channel first, e.g. `#launch-alerts`.
2. Go to <https://api.slack.com/apps> → **Create New App** → **From scratch**.
3. Name it (e.g. *Launch Intelligence Alerts*) and pick the Thrive Causemetics
   workspace. If the button is greyed out, the workspace requires admin
   approval for new apps — ask a Slack admin to approve the request.
4. In the left sidebar under *Features*, open **Incoming Webhooks** and turn
   **Activate Incoming Webhooks** on.
5. Click **Add New Webhook to Workspace**, choose the channel, **Allow**.
6. Copy the webhook URL (`https://hooks.slack.com/services/...`). It is a
   secret — anyone holding it can post to that channel as the app.
7. In GitHub: repo → **Settings → Secrets and variables → Actions → New
   repository secret**, name `SLACK_WEBHOOK_URL`, paste the URL. Do not commit
   it or paste it into a ticket.

**Optional repository variables** (same page, *Variables* tab):

| Variable | Default | Purpose |
|---|---|---|
| `SLACK_ALERT_LIMIT` | `5` | How many alerts a message carries |
| `DASHBOARD_URL` | `https://internal.thrivecausemetics.com/launch-dashboards/` | Base for the links in each alert |

**What gets posted.** `scripts/post_slack_alerts.py` reads the signals
`refresh_data.py` wrote into `data.js` — the same ones the "Needs attention"
panel shows — ranks them across every live launch, and posts the top N. Each
alert links to that launch's dashboard; the footer links to the hub.

Weekday runs post only what is new or has changed severity, and post nothing
at all when there is nothing new. Monday posts the full digest plus anything
that cleared during the week. State lives in `config/alert_state.json`,
committed by the workflow, so what was alerted and when is in git history.

Dry-run it without posting anything:

```bash
python scripts/post_slack_alerts.py --dry-run --digest
```

Delete an entry from `config/alert_state.json` to make that alert fire again.

## Database

**Not required.** Evidence: the app serves committed static files; the only
data dependency is `data.js`, produced by the GitHub Actions pipeline. No
Postgres add-on should be provisioned.

## Verification checklist (after deploy)

- [ ] `GET /api/health` returns `ok: true` with a recent `dataCutoff`
- [ ] `/` renders launch cards; `/launch.html?id=empowershine` renders KPIs
- [ ] `/launch-dashboards/` serves the same app (portal proxy path)
- [ ] `/scripts/refresh_data.py` and `/config/launches.json` return 404
- [ ] After the next morning data commit, Railway redeploys and `dataCutoff` advances
- [ ] Trigger service: a manual **Deploy** exits 0 (logs either a dispatch or
      `out-of-season cron entry`), and never logs `REFRESH_DISPATCH_TOKEN is not set`
- [ ] The morning after go-live, the `refresh-data` run shows event
      `workflow_dispatch` starting at ~6:00am LA — not `schedule` hours late
- [ ] `dataCutoff` equals yesterday's date when checked at 7:00am LA

## Rollback

Revert the offending commit on `main` (Railway redeploys the previous
state), or redeploy the last known-good deployment from the Railway UI
(human-gated).
